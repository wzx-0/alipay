## 🔄 执行过程

### Step0 - 初始化 TODO

- **输入**：FRD-前端、API 交互时序图、业务编码清单
- **产出**：`<TODO文件>` 中 stage04 区块（步骤进度表 + 子任务表，子任务**按业务功能点拆分**）
- **输出目录**：`<TODO文件>`

### Step1 - 前置检查

- **输入**：`<前端代码库根>` 当前状态、stage01/02 全部产物
- **产出**：前置检查结论（通过 / 阻塞项清单），写入 TODO
- **检查项**：
  1. `<前端代码库根>` 已存在可编译运行的项目骨架，**项目编译通过**
  2. 技术基座依赖齐全（按 `seehoo-dev-fe-guide` 要求）
  3. 上游产物完整：FRD-前端、业务编码清单、API 交互时序图均存在且互相一致
- **失败处理**：任一项不通过则阻塞，记入 TODO 异常并通知项目负责人；不替用户建骨架、不替用户改设计

### Step2 - 基础层落地

- **输入**：API 定义、API 交互时序图、业务编码清单
- **产出**：API 请求封装函数、接口类型声明（TS）、路由配置、状态管理 Store
- **使用 Skill**：seehoo-dev-fe-guide（加载 common.md + api-layer.md + page-layer.md）
- **输出目录**：`<前端代码库根>`
- **小验收**：项目编译通过

### Step3 - 按业务功能点实现 UI 层

- **循环单位**：Step0 TODO 子任务表中的每一条业务功能点，逐条迭代，每条完成后等待【OK】再继续下一条
- **确认子步骤**：每条功能点开始编码前，frontend-coding-expert 先列出该功能点的**待确认事项**（涉及组件类型、关键交互逻辑、数据流向等未明确点），主 Agent 转发给用户，收到【OK】+ 答案后再进入编码
- **输入**：对应业务功能点涉及的 FRD-前端、API 交互时序图、已落地的 API 封装/Store/类型
- **产出**：View 组件、Page 页面、表单/表格/弹窗等交互组件、样式文件
- **使用 Skill**：seehoo-dev-fe-guide（加载 common.md + component-layer.md + page-layer.md）
- **辅助 Skill**：列表页场景可选 `fd-filter-table`，详情页场景可选 `fd-detail-page`——子 Agent 据功能点类型决定是否调用，辅助 Skill 提供模板化快速产出能力，不替代 fe-guide 的规范约束
- **输出目录**：`<前端代码库根>`
- **小验收**：项目编译通过

### Step4 - 生成单元测试

- **输入**：Step2/3 产出的前端代码（路径：`<前端代码库根>`）、FRD-前端、业务编码清单、API 定义、API 交互时序图
- **产出**：与本次实现对应的单元测试代码（组件渲染、交互逻辑、API 调用 mock）
- **使用 Skill**：seehoo-dev-fe-unit-test
- **输出目录**：`<前端代码库根>`
- **小验收**：项目编译通过

### Step5 - 编译验收与交付

- **输入**：全量代码
- **产出**：stage04 完成报告（写入 TODO stage04 区块），含：
  - 全量编译结果
  - 单元测试生成范围说明
  - 与 stage02 设计的偏差列表（如有）
- **暂存代码**：执行 `git add <前端代码库根>`
- **验收门槛**：全量编译通过；未通过则记录异常并暂停本环节

## ⚠️ 本环节特殊约束

### 主 Agent 委派规则（防呆清单）

主 Agent 在委派任务时，**必须遵守以下规则**：

| 规则                      | 说明                                                              | 示例                                                                                                       |
| ------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **不指定文件路径/组件名** | 由 frontend-coding-expert 据 `seehoo-dev-fe-guide` 与现有骨架决定 | ❌ "在 `src/views/license/` 下建 `LicenseForm.vue`"<br>✅ "实现「营业执照新增」业务功能点的页面与表单组件" |
| **不指定技术选型**        | UI 库、状态管理方案、测试框架等技术细节由子 Agent 据规范决定      | ❌ "用 Element Plus 的 ElDialog 弹窗"<br>✅ "落地该业务功能点的弹窗交互组件"                               |
| **不指定实现细节**        | 只传递 SOP 中定义的产出名称与对应的设计产物路径                   | ❌ "表格加分页、搜索栏放上面、用 Composition API"<br>✅ "实现该业务功能点对应的列表页与查询表单"           |
| **不指定测试实现细节**    | 单元测试框架、测试文件名、mock 策略由子 Agent 据规范与骨架决定    | ❌ "用 Vitest 写 `LicenseForm.spec.ts` 并覆盖 5 个场景"<br>✅ "为本次实现代码生成对应的单元测试"           |
| **完整传递 4 要素**       | 必须包含：skill 名称、设计输入路径、输出目录、小验收命令          | 见上方模板                                                                                                 |

### 设计偏差处理

- frontend-coding-expert 在编码中如发现 FRD/API 定义/交互图之间冲突或不可实现，**必须停止编码**，将偏差写入 TODO 异常栏，由主 Agent 通知项目负责人决定：
  - 微调可在本环节内修复——记录偏差、继续编码
  - 涉及设计变更——回退到 stage01 / stage02 修订，stage04 暂停
- 严禁子 Agent 自行"改设计以迁就实现"

### 环节执行约束

1. **顺序执行**：Step0 → Step5 不可跳步
2. **小验收强制**：Step2/3/4 的小验收命令必须实际执行，且小验收仅以"项目编译通过"为标准，不得以"应当能通过"代替
3. **异常记录**：所有编译失败、设计偏差均记入 TODO
4. **执行前检查**：每个 Step 执行前，必须先阅读本文件中该 Step 的完整规范（输入、产出、输出目录、小验收）
5. **验收红线**：见下方「验收红线」章节

### ⚠️ 验收红线（禁止越权）

| 红线                                   | 说明                                                                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **禁止运行 `npm test` / `vitest run`** | Stage04 所有步骤的小验收 **仅有** 项目编译命令（如 `npm run build` / `vite build` / 等价编译命令），绝对不允许执行测试命令 |
| **禁止自行扩展验收标准**               | 不得在 SOP 规定的"编译通过"之外，额外要求"测试通过""覆盖率达标""Lint 无警告"等任何标准                                     |
| **禁止以"质量更好"为由偏离 SOP**       | 即使认为跑测试"更合理"，也不得自行添加。SOP 是唯一的验收标准                                                               |
