## 🔄 执行过程

### Step0 - 初始化 TODO

- **输入**：`<TODO文件>` 中 stage05 区块（编译结果、单元测试生成范围、偏差列表）
- **产出**：`<TODO文件>` 中 stage07 区块（步骤进度表 + 子任务表）
- **输出目录**：`<TODO文件>`

### Step1 - 代码审查

- **输入**：`<后端代码库根>` 业务源代码
- **产出**：审查报告（Markdown 文件，按 安全、性能、规范、简化 4 个维度分类）
- **使用 Skill**：
  - `seehoo-dev-be-guide`：审查基准，按规范原则识别问题
  - `seehoo-dev-be-review-report`：报告格式化，按固定模板输出
- **输出目录**：`<后端审查目录>`

### Step2 - 问题分流

- **输入**：Step1 产出的审查报告
- **产出**：问题分流结果（可在本阶段修复 / 需升级处理），写入 TODO stage07 区块
- **分流口径**：
  - **可在本阶段修复**：规范问题、局部安全问题、明显异常处理缺失、局部性能问题
  - **需升级处理**：涉及 FRD 变更、API 契约变化、DDL / 数据模型重构、权限口径调整等设计级问题
- **失败处理**：属于"需升级处理"的问题记入 TODO 异常并通知项目负责人；不得在本环节自行改设计

### Step3 - 人工确认

- **输入**：Step1 审查报告、Step2 问题分流结果、`<后端代码库根>` 业务源代码
- **产出**：人工确认结论
- **说明**：
  1. 主 Agent 完成 Step2 后，**主动列出审查报告摘要 + 问题分流清单**，等待人工回复
  2. 回复格式：【OK】确认通过，或提出调整要求
  3. 主 Agent 收到【OK】后，将分流结果写入 TODO，进入 Step4；若需调整，重新执行 Step2 或 Step1
  4. 确认完毕，本步骤完成

### Step4 - 代码修复与交付

- **输入**：Step3 人工确认后的可修复问题清单、`<后端代码库根>` 业务源代码、相关设计产物
- **产出**：
  - 修复后的代码
  - 修复变更摘要（写入 TODO stage07 区块）：逐条列出改动的类/方法名称及修复意图
- **使用 Skill**：seehoo-dev-be-guide
- **输出目录**：`<后端代码库根>`
- **小验收**：项目编译通过
- **暂存代码**：执行 `git add <后端代码库根>`

## 📋 执行模板

### backend-review-expert 执行模板（Step1）

启动 backend-review-expert 时，prompt **必须严格遵循以下格式**：

```
1. 首先调用 skill: seehoo-dev-be-guide，读取其编码原则文档作为审查基准
2. 【强制读取】对输入来源中的每个 .java 文件执行 read_file 获取实际代码内容，禁止仅凭文件名/类名推断
3. 【逐行审查】基于实际代码（而非推断）按 4 个维度（安全、性能、规范、简化）识别问题，记录每个问题的文件路径、行号、严重等级、问题描述、修复建议
4. 【交叉验证】对"未使用的错误码/类/方法"等判断，必须 grep 搜索确认引用关系
5. 【证据要求】审查报告中的每条问题必须附带实际代码片段（3-5行），禁止仅凭推断下结论
6. 调用 skill: seehoo-dev-be-review-report，将步骤 3-5 的结果按固定模板输出为 Markdown 报告
   ⚠️ 强制：必须将报告实际写入文件系统的 .md 文件（调用 write_file），禁止仅返回文本摘要
7. 输出目录：<后端审查目录>
```

### backend-coding-expert 执行模板（Step3）

启动 backend-coding-expert 时，prompt **必须严格遵循以下格式**：

```
   - 上下文：<已落地的相关类/包>
   - 输出目录：<后端代码库根>
4. 完成后执行小验收：<项目编译命令>，并报告结果
```

## ⚠️ 本环节特殊约束

### 主 Agent 委派规则（防呆清单）

| 规则 | 说明 | 示例 |
|------|------|------|
| **不指定审查角度** | 审查维度由 skill 的 4 个分类决定 | ❌ "重点审查 SQL 注入与越权"<br>✅ "对该需求源代码执行全面审查" |
| **不指定问题分级口径** | 严重程度由 backend-review-expert 判断 | ❌ "凡 SQL 注入直接判 blocker"<br>✅ 由审查专家判定 |
| **不指定修复实现细节** | 修复方案由 backend-coding-expert 据 skill 与现有骨架决定 | ❌ "把这个 Service 拆成两个方法并加缓存"<br>✅ "修复该审查报告指出的可落地问题" |
| **不扩大修复范围** | 只传递可修复问题清单与相关代码，不夹带新功能开发要求 | ❌ "顺手把台账导出功能也补上"<br>✅ "修复本阶段范围内的问题" |
| **审查完整传递 5 要素** | 必须包含：审查 skill 名称、报告 skill 名称、输入来源、输出目录、维度分类 | 见上方模板 |
| **修复完整传递 4 要素** | 必须包含：skill 名称、输入来源、输出目录、小验收命令 | 见上方模板 |

### 环节执行约束

1. **执行顺序**：Step0 → Step4 顺序执行，不可跳步
2. **小验收强制**：Step4 的小验收命令必须实际执行，不得以"应当能通过"代替
3. **异常记录**：所有审查执行异常、编译失败、设计级阻塞项均记入 TODO
4. **执行前检查**：每个 Step 执行前，必须先阅读本文件中该 Step 的完整规范（输入、产出、输出目录）
5. **人工确认门禁**：Step3 必须等待用户【OK】确认后，方可进入 Step4 代码修复；不得由子Agent自动跳过
