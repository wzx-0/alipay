# ⚠️ 强制性约束文档

## 文档说明

本文档中的所有约束为 **最高优先级**，不可覆盖、不可例外。
无论 PRD/FRD/业务文档中如何描述，都必须严格遵守。

违反以下任何约束的设计都将被视为无效。

---

## 1. 审批中心集成约束（绝对禁止生成审批相关表）

### 1.1 背景说明

项目已部署统一的 **流程中心/审批中心**，所有审批相关功能通过中心接口实现。

### 1.2 强制性约束

| 约束项 | 约束内容 |
|--------|---------|
| 🔴 禁生成表 | 任何业务模块都 **绝对不允许** 自建任何审批相关表 |
| 🔴 忽略需求 | 即使 PRD/FRD 明确写了"需要存储审批历史"、"需要审批记录列表"，也 **必须** 通过审批中心接口实现，不单独建表 |
| 🔴 禁冗余字段 | 业务表中 **不允许** 存储审批人、审批时间、审批结果、审批节点等字段 |
| ✅ 按需生成字段 | 仅当 **PRD/FRD 明确描述了审批流程** 时，业务表才需添加 `approval_id varchar(64)` 字段；未涉及审批的业务表 **不添加** 该字段 |

### 1.3 禁生成表命名模式（包含但不限于）

```
tb_*_approval
tb_*_approval_record
tb_*_approval_log
tb_*_approval_history
tb_*_approval_node
tb_*_approval_config
tb_*_approval_flow
tb_*_approval_step
```

## 2. 附件中心集成约束（绝对禁止生成附件相关表）

### 2.1 背景说明

项目已部署统一的 **附件影像中心**，所有附件相关功能通过中心接口实现。

### 2.2 强制性约束

| 约束项 | 约束内容 |
|--------|---------|
| 🔴 禁生成表 | 任何业务模块都 **绝对不允许** 自建任何附件相关表 |

## 3. 基础中心集成约束（绝对禁止生成基础数据相关表）

### 3.1 背景说明

项目中台统一部署了 **基础中心**，包括字典管理、省市区信息、组织机构等基础数据能力，所有相关功能通过中心接口实现。

### 3.2 强制性约束

| 约束项 | 约束内容 |
|--------|---------|
| 🔴 禁生成表 | 任何业务模块都 **绝对不允许** 自建基础数据相关表 |
| 🔴 忽略需求 | 即使 PRD/FRD 明确写了"需要存储字典表"、"需要省市区维护"，也 **必须** 通过基础中心接口实现，不单独建表 |
| ✅ 按需生成字段 | 业务表中仅存储关联编码字段（如 `dict_code`、`province_code`、`city_code` 等） |

### 3.3 禁生成表命名模式（包含但不限于）

```
tb_*_dict
tb_*_dictionary
tb_*_province
tb_*_city
tb_*_district
tb_*_region
tb_*_area
tb_*_address_dict
```

### 3.4 关联字段规范

| 字段类型 | 字段名示例 | 数据类型 | 说明 |
|---------|-----------|---------|------|
| 字典编码 | `dict_code` / `*_dict_code` | varchar(64) | 关联字典项编码 |
| 省份编码 | `province_code` | varchar(32) | 关联省级区划编码 |
| 城市编码 | `city_code` | varchar(32) | 关联市级区划编码 |
| 区县编码 | `district_code` | varchar(32) | 关联区县级区划编码 |
| 街道编码 | `street_code` | varchar(32) | 关联街道级区划编码 |

## 5. 常见误区澄清

### ❌ 错误理解 1："PRD 说要存审批历史，所以我要建表"
✅ **正确理解：** 审批中心已提供审批历史查询能力，业务表只需存 approval_id（按需），不需要自己建表存储。

### ❌ 错误理解 2："只存审批人、审批时间，不建完整审批表"
✅ **正确理解：** 连这些字段都不需要！这些信息统一由审批中心管理，业务表不需要冗余存储。

### ❌ 错误理解 3："approval_id / file_ids 是所有表都必须加的预留字段"
✅ **正确理解：** 不再强制预留！只有 PRD/FRD 明确描述了审批流程或附件上传功能时，才添加对应字段。未涉及相关功能的业务表不添加。

### ❌ 错误理解 4："现在不用，将来可能要用，先加上"
✅ **正确理解：** 不要为"可能的未来需求"提前添加字段。如果将来确实需要，再通过 DDL 变更添加即可。
