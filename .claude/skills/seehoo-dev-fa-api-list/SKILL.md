# API 清单自动生成技能

## 概述

本技能用于从PRD自动提取所有流量入口（API/Job/MQ），分配编号，输出结构化的API清单文档。

### 核心原则

1. **编号唯一**：每个入口必须分配唯一编号，不得与已有编号冲突
2. **编号规范**：遵循公司编号规则，从全局 API 定义索引中读取已分配范围
3. **完整覆盖**：PRD中所有业务操作对应的入口必须全部列出，不遗漏
4. **分类清晰**：API、Job、MQ 三类入口分别列出

### 编号规则

| 类型 | 格式 | 示例 |
|------|------|------|
| API | `A{业务领域2位}{业务模块2位}{序号3位}` | `A0101001` |
| Job | `J{业务领域2位}{业务模块2位}{序号3位}` | `J0101001` |
| MQ  | `M{业务领域2位}{业务模块2位}{序号3位}` | `M0101001` |

## 输入要求

- **PRD文档路径**：产品需求文档的文件路径
- **需求编号**（可选）：用于文档命名，如 `20260306`
- **需求名称**（可选）：用于文档命名，如 `营业执照管理`

## 输出文档

### 文件命名

```
API清单-{需求编号}-{需求名称}.md
```

### 标准章节结构

#### 文档头

```markdown
# API 清单 - {需求编号} - {需求名称}

| 来源PRD | 生成日期 | 文档版本 |
|---------|---------|---------|
| xxx.md  | 2026-xx-xx | v1.0 |
```

#### 1. API 入口

| API编号 | API名称 | 用途 | 请求方式 | 所属业务操作 | 权限 |
|---------|--------|------|---------|------------|------|
| A0101001 | 营业执照入库 | 新增入库 | POST | 新增入库 | 档案管理员 |

> 注：仅允许 GET 和 POST 请求，遵循公司 API 规范。

#### 2. Job 入口（如有）

| Job编号 | Job名称 | 用途 | 触发方式 | 所属业务操作 |
|---------|--------|------|---------|------------|
| J0101001 | 过期执照清理 | 定时清理 | Cron | 数据清理 |

#### 3. MQ 入口（如有）

| MQ编号 | 消费者名称 | 用途 | 消息来源 | 所属业务操作 |
|--------|-----------|------|---------|------------|
| M0101001 | 入库结果通知 | 异步通知 | 影像中心 | 新增入库 |

> Job 和 MQ 入口如无对应章节可省略。

## 生成步骤

### Step 1：读取PRD

1. 读取PRD文档完整内容
2. 识别PRD中的业务模块（通常按章节划分）
3. 从每个业务操作推导 API 入口
4. 识别定时任务（Job 入口）和异步消费（MQ 入口）

### Step 2：分配编号

1. 从全局 API 定义索引中读取已分配范围
2. 确定起始序号（最大已用序号 + 1）
3. 为每个入口分配编号

### Step 3：输出文档

按照标准章节结构输出文档：`API清单-{需求编号}-{需求名称}.md`

---

## 质量检查清单

生成API清单后，必须检查以下项目：

### 完整性检查
- [ ] PRD中所有业务操作都有对应的入口
- [ ] API、Job、MQ 分类正确，无遗漏

### 编号检查
- [ ] 编号格式正确（A/J/M + 领域2位 + 模块2位 + 序号3位）
- [ ] 编号无重复、无跳号
- [ ] 起始序号与全局索引中的已分配范围一致

### 一致性检查
- [ ] API名称与用途描述准确，与PRD一致
- [ ] 请求方式仅使用 GET/POST
- [ ] 所属业务操作描述清晰

## 注意事项

1. **不遗漏PRD内容**：PRD中所有业务操作都必须有对应的入口
2. **编号不冲突**：分配前必须检查全局 API 定义索引，确保不冲突
3. **权限要明确**：每个 API 入口必须标注所需权限/角色
4. **无则省略**：Job/MQ 入口如无则不生成对应章节
