# api-layer.md：API 封装层规范

## API 请求封装函数

### 原则

- 每个 API 接口对应一个封装函数，函数名以 `fetch` / `post` / `put` / `delete` 等动词开头，后接业务语义名
- 函数签名必须与 stage02 API 定义文档中该接口的请求参数和响应结构对齐
- 封装函数统一使用骨架已有的请求库和请求实例（如骨架已配置的 axios 实例或 fetch wrapper）
- 不得在封装函数内硬编码 URL，路径参数和查询参数通过函数入参传入

### 类型声明

- 每个 API 接口的请求参数和响应结构必须有对应的 TypeScript 类型声明
- 类型命名：`XxxRequest` / `XxxResponse`，与接口业务语义对应
- 类型字段必须与 API 定义文档的字段名、类型完全一致
- 业务编码清单中的枚举字段，在类型中使用对应的枚举类型或常量引用

### 错误处理

- 遵循骨架已有的错误处理机制（全局拦截器、统一错误码等）
- 封装函数不做额外的 try-catch 包装，除非骨架模式要求
- 不自行定义新的错误码体系

## 路由配置

### 原则

- 路由结构应反映业务模块划分，与 FRD-前端中的页面清单对齐
- 路由配置方式遵循骨架已有的路由注册模式（静态配置 / 动态加载 / 模块化拆分）
- 路由路径命名遵循骨架既定风格，新模块路由挂载在骨架既定的路由根节点下
- 路由 meta 信息（权限、标题等）遵循骨架已有的 meta 字段约定

### 路由与页面对应

- 每个路由项对应一个页面组件，路由 path 与页面语义名一致
- 不在路由中直接引用 UI 级组件，路由只引用 Page 级组件

## 状态管理 Store

### 原则

- 使用骨架已有的状态管理方案（如骨架使用 Pinia 则用 Pinia）
- Store 按业务模块划分，一个模块一个 Store 或按骨架既定拆分方式
- Store 中的状态结构与 API Response 类型对齐，不做冗余转换
- Store 只管理跨组件共享的状态，组件内部状态留在组件内

### 状态边界

- API 调用结果存入 Store，但 API 调用本身由 API 封装函数发起
- Store action 调用 API 封装函数，不直接在 Store 内写请求逻辑
- 不在 Store 中存储可从 props 或路由参数获取的数据

### 数据流向

- 页面 → Store → API 封装函数 → 后端，单向数据流
- 页面组件通过 Store 获取共享数据，通过 props 获取父组件传递的数据
- 不在 UI 组件中直接调用 API 封装函数（除独立弹窗/独立表单等特殊场景）
