# common.md：前端通用规范

## 命名约定

### 原则

命名风格必须与项目骨架已有代码保持一致。如果骨架内存在多种风格，以骨架入口文件/README/配置文件中声明的风格为准。

### 文件命名

- 组件文件：遵循骨架既定的组件文件命名风格（如 PascalCase 或 kebab-case）
- 非组件文件（utils、helpers、constants）：遵循骨架既定的工具文件命名风格
- 类型声明文件：与骨架既定类型文件命名风格一致

### 变量与函数命名

- 函数名：camelCase，动词开头（`fetchXxx`、`handleXxx`、`formatXxx`）
- 常量：UPPER_SNAKE_CASE 或遵循骨架既定风格
- 类型/接口名：PascalCase，名词开头
- 组件 props：camelCase，与骨架 UI 库的 props 风格一致

### 业务编码引用

业务编码清单中的模块编码和枚举编码，在代码中必须作为常量或类型使用，不得硬编码字符串散落各处。

## 目录组织

### 原则

目录结构必须遵循骨架已有的组织方式。不自行创建骨架中不存在的顶层目录或改变骨架的分组逻辑。

### 常见骨架目录模式

骨架可能采用以下任一模式（以骨架实际为准）：
- **按技术类型分组**：`src/api/`、`src/views/`、`src/components/`、`src/store/`、`src/types/`
- **按业务模块分组**：`src/modules/{module}/api/`、`src/modules/{module}/views/` 等
- **混合模式**：公共层按技术类型分组，业务层按模块分组

### 新增业务模块放置规则

- 如果骨架按技术类型分组：各层文件放入对应技术目录下的业务子目录
- 如果骨架按业务模块分组：全部文件放入对应模块目录下
- 如果骨架混合模式：公共代码放入技术目录，业务代码放入模块目录

## 技术基座依赖

### 原则

所有技术基座（UI 库、请求库、状态管理、路由、构建工具等）以骨架 `package.json` 已安装的版本为准。

### 禁止行为

- 不引入骨架未安装的新依赖包
- 不升级骨架已有的依赖版本
- 不替换骨架已有的技术方案（如骨架用 Pinia 则不用 Vuex）

### 依赖声明方式

新增的业务模块如果需要骨架已有基座的能力，直接引用骨架已安装的包，不重复安装。
