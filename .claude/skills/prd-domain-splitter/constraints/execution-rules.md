# PRD拆分执行约束规则

## ⚠️ 优先级说明
本文件规则优先级最高，与其他规范冲突时以本文件为准。

---

## 🔴 绝对禁止规则

| 规则 | 约束内容 |
|-----|---------|
| **禁止脑补** | 所有内容100%来自原始PRD，禁止生成任何不存在的功能描述 |
| **禁止空文件** | 只提到名称但无详细描述的功能 → 放入【待拆分清单】 |
| **禁止跳跃层级** | 严格按 `#`/`##`/`###` → L1/L2/L3 一一对应 |
| **禁止拆分附件功能** | **涉及附件/文件管理 → 直接放入待拆分清单** |
| **禁止拆分审批功能** | **涉及审批流程/节点/规则 → 直接放入待拆分清单** |

---

## 🟡 执行流程（两阶段）

### 阶段一：生成业务领域清单
| 步骤 | 操作内容 |
|-----|---------|
| 1 | 扫描PRD所有标题，建立章节索引表 |
| 2 | 识别L1/L2/L3层级边界，识别附件/审批功能 |
| 3 | 生成 `_业务领域清单.md`（纯文本树形结构、编码、合并建议） |

### 阶段二：按确认的清单执行拆分
| 步骤 | 操作内容 |
|-----|---------|
| 1 | 根据用户确认，确定L3合并策略 |
| 2 | 提取L3功能点完整内容，不做任何改写 |
| 3 | 执行标准Markdown格式转换（见下文） |
| 4 | 生成 `_待拆分清单.md` 和 `_章节处理对账表.md` |

---

## 🟠 附件与审批功能识别规则

### 📎 附件相关功能（放入待拆分）
- 关键词：`附件`、`附件上传`、`文件上传`、`文件管理`、`文档管理`
- 功能：文件存储/预览/下载/版本管理、附件权限/审批/归档

### ✅ 审批相关功能（放入待拆分）
- 关键词：`审批`、`审批流程`、`审批节点`、`审批规则`、`审批配置`
- 功能：流程审批、多级审批、审批驳回/通过、审批人/条件配置

---

## 🟢 L3功能点判定标准

### ✅ 必须创建L3文件（满足任意一项）
- 原始PRD中有独立三级标题章节
- 有完整CRUD操作描述
- 有完整业务流程描述（申请→审批→结果）
- 有具体页面字段定义 + 操作说明

### ⚠️ 放入待拆分清单
- 只提到功能名称，无详细描述
- 缺少完整业务操作流程
- 内容行数 < 40行且闭环不完整
- 涉及附件/文件管理相关功能
- 涉及审批流程/节点/规则相关功能

### 📦 L3合并规则（基于内容完整性的智能建议）

#### 🎯 内容完整性评估标准（合并决策依据）
| 评估维度 | 完整业务闭环（≥3项满足） | 内容不完整（<3项满足） |
|---------|------------------------|----------------------|
| 功能描述 | ✅ 有明确功能定位 | ⚠️ 仅提到名称，无详细说明 |
| 业务流程 | ✅ 有完整流程描述（申请→处理→结果） | ⚠️ 只有零散节点描述 |
| 页面字段 | ✅ 有具体页面字段定义 | ⚠️ 无字段描述或不完整 |
| 操作说明 | ✅ 有按钮/操作逻辑说明 | ⚠️ 无操作说明 |
| 内容行数 | ✅ ≥ 80行 | ⚠️ < 50行 |

---

#### 📋 合并建议矩阵

| 场景 | 内容完整性评估 | 合并建议 | 说明 |
|-----|--------------|---------|------|
| **单个L3功能独立完整** | ✅ 完整业务闭环 + ≥80行 | ❌ **不合并，独立成文档** | 功能边界清晰，可独立开发 |
| **同一业务流程前后环节** | ✅ 各自完整但流程强关联 | ⚠️ **评估后决定** | 若单独都≥100行则独立，否则合并 |
| **多个配置类小功能** | ⚠️ 各自不完整，属于同一配置域 | ✅ **必须合并** | 如：各种参数配置、规则配置 |
| **单个L3内容简短** | ⚠️ < 50行 + 无完整闭环 | ✅ **必须合并** | 内容不足以支撑独立开发 |
| **跨L2但业务高度相关** | ✅ 各自完整但属于同一大流程 | ⚠️ **谨慎评估** | 优先保持L2边界，仅在极端情况合并 |

---

#### ✅ 合并操作规范
1. **分隔方式**：合并后的不同L3功能点之间用 `---` 分隔
2. **命名规则**：合并文档以所属L2子域命名 `PRD-{L1编码}-{L2编码}-{L2名称}.md`
3. **大小限制**：合并后的文档总页数 ≤ 10页（约2000行）
4. **边界清晰**：合并时必须保留每个L3功能的独立标题，便于后续拆分
5. **对账记录**：所有合并的L3必须在对账表中明确标注"已合并入L2/L3"

## 🔵 格式处理规则

### 🎯 核心原则
**提取纯文字内容，按照标准Markdown格式输出**

---

### 🚨 强制执行：调用通用格式转换脚本

**禁止手写正则清理脚本**。必须直接调用本技能内置的通用脚本：

```
constraints/format-convert.ps1
```

#### 调用方式（PowerShell）

```powershell
& 'C:\Users\admin\.qwen\skills\prd-domain-splitter\constraints\format-convert.ps1' `
    -InputFile  '<源Markdown文档绝对路径>' `
    -OutputFile '<输出PRD文件绝对路径>' `
    -StartLine  <起始行号(1-based)> `
    -EndLine    <结束行号(1-based,inclusive)> `
    -L2Title    '<L2标题文本>'
```

#### 脚本能力（通用 Markdown 处理）

| 类别 | 处理动作 |
|------|---------|
| 保留 | `#`/`##`/`###` 标题、有序/无序列表、纯文字、加粗 `**` |
| 丢弃 | Markdown 表格行（整行）、代码块（```...```）、图片、HTML 标签、行内代码 |
| 转换 | `###` → `##`（L3标题）、链接 `[文字](url)` → `文字`、`1)`→`1.`、`A./a./i.` → `-` |
| 插入 | 不同 L3 之间自动插入 `---` 分隔符 |
| 头部 | 自动添加 `# {L2Title}` 文档头 |

#### 设计原则
- 不依赖任何具体文档的格式特征
- 对任何 Markdown 文档都能产出干净的"标题+列表+纯文字"骨架
- 输出后自动打印校验摘要（行数、各级标题数、分隔符数、残留 `|`/`<>` 计数）

---

### ✅ 输出规范
- 标题前后、段落之间保留1个空行
- 列表统一左对齐，一级列表无缩进，二级缩进2空格
- 加粗标记 `**` 正确保留语义强调
- 同一L2下的不同L3功能点之间用 `---` 分隔
- 所有文字语义100%完整保留

---

## 🟣 输出文件规范

### 文件命名格式
| 层级 | 命名格式 |
|-----|---------|
| **L2功能文档** | `PRD-{L1编码}-{L2编码}-{L2名称}.md` |
| **L3合并文档** | 合并多个L3时，以L2功能命名 |

### 辅助输出文件
| 文件名 | 内容要求 |
|-------|---------|
| `_业务领域清单.md` | 层级结构、编码分配、合并建议、确认指引 |
| `_待拆分清单.md` | 功能点名称 + 未拆分原因 + 精确行号范围 |
| `_章节处理对账表.md` | 所有三级标题的处理状态 |

## ✅ 校验清单

### 业务领域清单（阶段一）
- [ ] 纯文本树形结构展示所有层级
- [ ] 每个L1/L2都有两位数字编码
- [ ] 每个L3都标注了行数、合并建议、文件名
- [ ] 附件/审批功能已标注为待拆分

### 拆分完成（阶段二）
- [ ] 所有内容100%来自原始PRD，无脑补
- [ ] 严格按标题层级拆分，无跳跃
- [ ] 附件/审批功能已放入待拆分清单，未拆分
- [ ] L3文件数 + 待拆分数 + 已合并数 = 三级标题总数
- [ ] 合并文件用 `---` 分隔功能点
- [ ] 所有文件名符合命名规范
- [ ] 已移除所有表格符号和多余前导空格
- [ ] 已转换为标准Markdown标题和列表格式
- [ ] 段落之间只有1个空行，加粗标记正确保留
- [ ] 输出为干净的标准Markdown文档

---

## 🚨 违规处理
校验不通过时立即重新执行，不输出任何文件。待拆分清单宁可多列，不可遗漏。
