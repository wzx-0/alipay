# 框架适配

创建任何单元测试前阅读本文件。

## 测试目录结构

- 测试源码目录通常与主源码保持相同的包结构，即 `src/test/java/{package-path}/` 对应 `src/main/java/{package-path}/`
- 测试类名一般以被测试类名 + `Test` 结尾
- 如果项目已有不同的测试组织方式（如按功能模块分目录），则遵循项目现有惯例

## 不要发明新的测试技术栈

始终先检查项目现状。

复用项目当前的：

- 测试源码目录布局
- 包结构
- 文件命名模式
- 测试框架
- Mock 框架或 Fake 策略
- 断言风格
- Fixture 辅助方法
- 测试基类

## 检查清单

编写测试前检查：

1. 已有测试存放位置
2. 测试类如何命名
3. 测试使用 Mock 对象、Stub 还是真实 Spring 上下文
4. 断言使用普通断言、Fluent Assertions 还是自定义辅助方法
5. 是否有可复用的共享测试工具类

## 生产代码调整

如果生产代码难以测试：

- 采用最小的安全调整
- 不要仅为了满足测试风格而重写业务结构
- 不要改变业务行为

可接受的示例：

- 抽取一个纯函数的小型辅助方法
- 在项目已有风格允许的前提下，放宽协作者注入点的可见性
- 复用已有的构造函数或 setter

不可接受的示例：

- 重新设计模块结构
- 为了让断言更容易而改变领域规则
- 在已有代码库中引入全新的测试架构

## 与项目风格匹配

项目已有示例时，紧密跟随。

包括：

- 测试方法命名
- Setup 模式
- Mock 编排模式
- 断言措辞
- 包放置

当没有示例时，选择最轻量、最常规的单元测试风格，同时保证编译通过并最小化未来不一致。
