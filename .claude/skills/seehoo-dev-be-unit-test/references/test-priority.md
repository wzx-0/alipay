# 测试优先级

本文件用于决定编写多少用例以及按什么顺序编写。

## 核心原则

少量有意义的测试优于大量浅层测试。

## 用例设计基线

对每个重要业务目标，尽量覆盖：

1. 主成功路径
2. 关键失败路径
3. 边界或异常路径

## 主成功路径

证明业务动作在有效输入下能够成功。

示例：

- 有效请求下创建成功
- 在允许状态下提交成功
- 查询正确返回映射结果

## 关键失败路径

证明最重要的保护规则已生效。

示例：

- 非草稿状态下提交失败
- 唯一编码已存在时保存失败
- 权限前置条件不满足时操作失败

## 边界或异常路径

证明在合法业务空间边界上的行为正确。

示例：

- 空值或缺失必填值
- 不支持的枚举值
- 协作者响应为空
- 无匹配记录

## 优先级顺序

如果无法一次写完所有测试，按此顺序进行：

1. 业务关键 Service 方法
2. 状态流转规则
3. 校验与异常分支
4. 映射或转换逻辑
5. 次要辅助行为

## 避免虚假的完整性

不要用低信号用例 inflate 测试数量：

- 用大量相似输入重复同一分支
- 测试项目未定制的框架行为
- 测试私有实现细节而非外部可见行为

## 合适的停止点

满足以下条件时可以停止：

- 每个关键业务方法至少有一个成功断言
- 每条关键规则至少有一个失败断言
- 最重要的边界场景已覆盖
- 继续添加测试大多是重复信号
