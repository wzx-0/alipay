# Seehoo 后端单元测试

本技能用于为指定的后端 Java 业务代码生成单元测试。

## 目标

为指定的后端 Java 代码（通常为 Service 层业务逻辑）生成对应的单元测试代码。

本技能仅用于**编写测试代码**，不负责执行测试闭环。

## 调用方必须提供

- **待生成测试的文件范围**：git diff 命令、文件列表，或目录路径
- **上游设计产物路径**：FRD（后端）、业务编码清单、API 定义、API 逻辑文档（可选，缺失时跳过对应断言并在注释中注明）

## 工作流程

1. 按调用方指定的方式确定文件范围。只保留业务层文件（Controller、Service、Entity、Mapper、DTO/VO、常量枚举），排除测试类、配置类、基础设施类。
2. 完整读取每个待测试的业务层文件。
3. 阅读可用的上游设计产物，提取关键业务规则和校验约束。
4. 判断哪些类需要编写测试。
5. 生成遵循项目现有框架、命名、断言风格和 Mock 风格的测试代码。
6. 变更保持最小化，与当前代码库对齐。
7. 以阶段级验收规则收尾：项目编译通过。

## 边界

- 仅针对调用方指定范围内的文件生成测试。
- 仅保留业务层文件，排除测试类、配置类、基础设施类。
- 不要试图偿还历史测试债务。
- 不要为了让测试更容易而改写设计文档。
- 不要扩展到新功能开发。
- 本技能仅编写测试代码，不负责执行测试闭环。
- 如果代码难以测试，优先采用最小的生产代码调整，且不改变业务行为。

## 测试范围优先顺序

开始确定详细测试目标前，先阅读 [references/test-scope.md](references/test-scope.md)。

默认优先级顺序：

1. Service 层业务逻辑
2. 参数校验与异常分支
3. 状态流转与规则判定
4. 枚举或常量转换逻辑
5. 仅在项目已有直接测试该层的惯例时，才测试 Repository 或 Mapper 层

## 覆盖度要求

开始编写用例前，先阅读 [references/test-priority.md](references/test-priority.md)。

对每个重要业务目标，尽量覆盖：

- 一条主成功路径
- 一条关键失败路径
- 一条边界或异常路径

目标是覆盖业务风险，不是追求虚荣覆盖率。

## 框架适配规则

创建任何测试文件前，先阅读 [references/framework-adaptation.md](references/framework-adaptation.md)。

必须继承项目现有风格，而不是另创一套测试写法。

至少检查：

- 测试源码目录结构
- 测试命名模式
- 单元测试框架
- Mock 库或 Stub 风格
- 断言风格
- 辅助基类或 Test Fixture

## 产出要求

产出：

- 与当前实现对应的单元测试文件
- 仅在明确需要时，生成最小配套的 Test Fixture 或辅助类

避免产出：

- 针对普通 DTO/VO 存取方法的测试
- 针对无业务分支的框架模板代码的测试
- 大型集成测试套件（除非项目本身就将其作为默认单元测试模式）

## 停止条件

遇到以下情况时停止编码并上报调用方，不要自行猜测：

- 指定范围内没有可测试的 Java 业务层文件
- 项目无可识别的测试基础设施
- FRD、API 定义与代码行为之间存在冲突，影响测试断言的预期
- 要生成有意义的测试必须改动设计
- 最小变更也无法保证编译通过
